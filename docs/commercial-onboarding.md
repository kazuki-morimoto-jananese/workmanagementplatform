# 企業導入と運用手順

## 現在の販売可能範囲

現在は**1社ごとに独立したWorknest環境を用意する構成**。同じURL内に複数企業を登録して切り替えるマルチテナントSaaSではない。現環境に別会社を追加して使い回さない。会社ごとにWorker・Durable Object・秘密設定・OAuth・管理者を分離し、別URLを使う。

企業用の設定生成を `scripts/prepare-tenant.mjs` に追加した。生成だけでは公開も課金契約も行わない。既存の会社環境は変更しない。

## 導入の順序と担当

| 手順 | 操作・確認 | 担当 | 完了条件 |
| --- | --- | --- | --- |
| 1 要件確認 | 利用人数、会社ドメイン、組織、正となるシステム、保存対象、データ持出し可否 | 導入担当＋顧客 | 対象データと権限が合意できる |
| 2 環境作成 | 企業別設定を生成し、顧客用Workerへ配備 | 導入担当 | 別URL・別DB・別秘密設定で起動 |
| 3 初期管理者 | SETUP_TOKENを安全に受け取り、メール・パスワードで初期登録 | 顧客管理者 | 登録後の初期セットアップが閉じる |
| 4 組織・権限 | 会社→事業部→部→グループ→チーム登録、管理者とメンバー追加 | 顧客管理者 | 氏名・メール・所属が揃う。初期パスワード変更 |
| 5 マスタ移行 | アカウントID・氏名・円単位・列対応をプレビュー | 営業運用者 | 件数・合計・0と空欄が元データと一致 |
| 6 目標・集計 | 月ごとに個人目標と所属を保存 | 営業管理者 | 部合計＝配下の担当者目標の合計。未所属を確認 |
| 7 外部連携 | Docs本人認証、任意のCalendar、Geminiの設定と架空文テスト | 顧客本人＋Google管理者 | 実際に必要な範囲だけ許可される |
| 8 CRM移行 | 顧客担当者登録、または受付専用トークン発行→受信確認→反映 | 管理者＋連携担当 | 安定外部IDと再送確認、エラー時の再取込担当が決定 |
| 9 試行 | 週次会議2〜4回、ヨミ・議事録・次回タスクを運用 | 対象部署 | 元表との照合、入力負担と漏れの確認 |
| 10 継続運用 | 定期エクスポート、復元訓練、退職者停止、トークン更新 | 顧客管理者＋保守担当 | バックアップ担当・間隔・保存先・復旧手順が決定 |

データ連携に今回追加した「運用開始チェック」で組織・メンバー・アカウント・個人目標・本人Google・Geminiキーの設定状況を確認できる。ただし疎通試験・バックアップ復元試験の代わりにはならない。

## 企業別Cloudflare環境の設定例

以下は新規顧客の例。既存会社の設定ファイルでは実行しない。

```powershell
node scripts/prepare-tenant.mjs example https://worknest-example.YOUR-SUBDOMAIN.workers.dev example.com
npm.cmd run build
npx.cmd wrangler deploy --config .secrets/tenants/example/wrangler.json
npx.cmd wrangler secret bulk .secrets/tenants/example/secrets.json --config .secrets/tenants/example/wrangler.json
```

Cloudflareへ事前にログインし、対象アカウントを明示する。企業IDはWorker名の一部になるため、アカウント内で一意にする。別Workerには別のDurable Object名前空間が作られる。公開後、生成したSETUP_TOKENで初期管理者が登録する。生成ファイルは秘密情報を含むためGitに追加しない。

Google接続は企業別のクライアント・リダイレクトURIを作成し、**その企業のWorker**へGOOGLE_OAUTH_CLIENT_ID / GOOGLE_OAUTH_CLIENT_SECRET / GOOGLE_OAUTH_REDIRECT_URIを登録する。現在の `connect-google.cmd` は現在の会社向け補助スクリプトなので、新規顧客への汎用設定にはそのまま使わない。Geminiキーも会社別Workerへ設定する。

カレンダーを使う場合は対象Google CloudプロジェクトでGoogle Calendar APIを有効にし、本人が「カレンダー閲覧を許可して接続」を押す。会社のAPI制御により管理者の許可が必要な場合がある。WorkspaceのGoogle接続はWorknestへのログインSSOではなく、データ取得のための認可。

## 組織別サマリーのルール

個人目標の編集画面に月次の所属を追加。明示設定した所属が優先、未保存の所属は同名メンバーの現在の所属で補完する。Excel氏名とメンバー名が違う場合は自動推測せず所属を設定する。月次所属を保存した後の異動は他の月の所属を変更しない。既存の部→チームの構成も引き続き読める。

1人はその月1組織に割り当て、親組織には配下の個人を一度ずつ積算する。所属未設定は別枠。個人が担当する全アカウントのヨミ・Gトレをその個人の所属で集計する。アカウントの組織を基準とする分割売上配賦ではない。兼務の比率配賦は未対応。

組織フィルターは集計・表示のための機能で、部署別の閲覧制限ではない。現行の営業情報はワークスペース内で共有する。タスクの非公開制御とは別である。大企業向けの部署別財務ACLが必要なら契約前に追加する。

## 商用化のボトルネックと対応方針

| ボトルネック | 今回までの対応 | 販売前・拡販前の残作業 |
| --- | --- | --- |
| 顧客間の混在 | 企業別環境設定生成・独立DB方式 | 配備台帳、リリース一括管理、監視。セルフサービスSaaSにはテナントID・全APIの分離テストが別途必要 |
| Googleの認可に手作業が多い | 本人OAuth・必要時のCalendar追加認可 | 顧客所有プロジェクト方式か、提供者の検証済みOAuthアプリ方式かを決定。審査と利用規約整備 |
| 外部共有禁止 | Docs本人認証・Excel代替 | 外部システムへの保存自体の会社承認が必要。技術では社内規程を迂回しない |
| 製品ごとのID・列が違う | Excel列対応、CRM共通受付契約、名前空間と再送制御 | 各製品アダプター、顧客ID統合、双方向更新時の正本定義 |
| データ権限・退職者 | 管理者／メンバー、アカウント停止、非公開タスク、トークン失効 | SSO/SAML/OIDCログイン、MFA、SCIM、細かな権限ロール・部署別ACLは未実装 |
| データ保全 | 永続DB、変更履歴、エクスポート・復元、取り込み履歴 | 別保管先の自動バックアップ、復旧時間と許容損失の合意、定期復元訓練、保持・削除ポリシー |
| 連携障害 | HTTPエラー、日次同期状態、受付確認、競合拒否 | 監視通知・再送キュー・担当者エスカレーション。新規APIの401/400等は送信元で記録 |
| MA配信 | 流入元・段階・連絡許可・次回タスク | 配信停止・同意証跡・レート制限・苦情対応・配信事業者を整えてからメール配信 |
| AIの契約・情報管理 | サーバー側キー、架空文接続テスト、根拠確認して数値反映 | 顧客の情報取扱方針に合うプラン・契約、入力データ範囲、利用上限を決定 |
| 契約・請求・サポート | 設定生成・導入チェック・手順書 | 利用規約、プライバシーポリシー、委託契約、課金、請求、解約・データ返却、SLAは別途整備 |

これらの残作業があるため、現時点を「一般企業向けの商用SaaSとして完成」とは表現しない。まずは対象部署を限定した導入支援付きの試行で入力負担と運用品質を検証する。無料枠のままで全社規模・SLAを保証しない。将来の有料プラン移行は実測容量・負荷と顧客合意に基づいて判断する。
