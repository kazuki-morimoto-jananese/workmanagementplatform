# 販売に向けた課題と実装範囲

2026-09-06時点。社内共有の1社・1ワークスペースで運用するMVPとして評価しました。v2.3で運用基盤を拡充していますが、複数顧客を1つの環境に収容するSaaSの完成版ではありません。

| 優先度         | 課題と影響                                      | 今回の対応・次の作業                                                                                                                                                                                    |
| -------------- | ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 最優先         | 操作履歴が500件で消え、過去の変更内容を追えない | 制限撤廃。主要データの更新前後・削除・実行者の監査保存、基準状態の移行、履歴閲覧・JSON出力を実装                                                                                                        |
| 最優先         | 手動バックアップだけでは保存忘れが起こる        | 稼働中の日次バックアップ、整合性検査、状態表示、手動実行、空の別フォルダーへの復元コマンドを実装。別ストレージ複製・監視・定期復元訓練は運用設定が必要                                                  |
| 高             | 議事録の分散と更新による出典消失                | Google文書取込・任意更新・改訂版保存・旧タスクの出典維持を実装                                                                                                                                          |
| 高             | AIが既存の数字を誤って書き換える                | 原文根拠・数値・単位の検証、確認反映、任意の当月空欄への自動反映、既存値保護、同時編集検査、上限・失敗表示・再開を実装                                                                                  |
| 高             | 部門名の表記揺れと他部署からの依頼漏れ          | 共通組織マスタ、本人所属登録、プロジェクト参加者、部署を横断した参加・担当一覧、複数タスク担当を実装                                                                                                    |
| 販売前必須     | 顧客間のデータ分離                              | 現状は1社ごとにアプリ・DB・秘密鍵・バックアップを分離する構成。共有SaaS向けtenant_id、全APIの境界強制、越境テストは未実装。複数社を同じワークスペースへ登録しない                                       |
| 販売前必須     | 社内の閲覧・編集権限が一律                      | 現在は管理者/メンバー、メンバー発行・停止、強制初回パスワード変更、期限付きセッションまで。部門限定・非公開プロジェクト・閲覧専用・外部ゲストの権限は未実装。導入先の機密区分に合わせた仕様が必要       |
| 販売前必須     | 認証基準と退職者管理                            | Googleログイン/SSO、MFA、SCIM、組織の退職イベントとの連携は未実装。現状は管理者が停止すると既存セッションも無効化。導入先の認証基盤を選んで実装する                                                     |
| 販売前必須     | 運用品質を保証できる測定がない                  | HTTPS・永続ボリューム・ヘルスチェック・CIあり。外部監視、通知先、障害対応、実測に基づくSLA/RPO/RTO、脆弱性診断・負荷試験は別途必要                                                                      |
| 規模拡大前     | 長期蓄積でDBとレスポンスが大きくなる            | 監査はインデックス付きの100件ページング。通常のタスク・営業初期読込は全件取得を含む。実データ規模で測定し、サーバー検索・ページング・原文の遅延読込・ジョブ専用ワーカー・必要に応じPostgreSQLへ拡張する |
| 契約方式決定後 | 課金・契約・退会・データ移行                    | プラン、席数課金、請求、契約、退会時エクスポート・削除、保存期間ポリシーは未実装。販売方式と顧客要件が決まってから設計する                                                                              |

課金や顧客を分離する仕組みを形だけ付けると、既存の全社共有モデルと矛盾します。そのため今回の実装は、社内運用でも直ちに必要になる保存・復元・入力の信頼性・共同作業を優先しました。販売の初期構成は顧客ごとに環境を分離する方式が適しますが、これは外部提供の承認や品質保証を意味しません。

Google/Gemini設定、データの共有範囲、履歴の仕様は[運用・連携ガイド](operations-and-integrations.md)を参照してください。
